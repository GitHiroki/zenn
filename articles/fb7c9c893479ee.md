## まずはじめに

久々にOllamaのドキュメントを開いたら、見慣れない単語が目に入った。

量子化（Quantization）

以前にOllamaを触ったとき（[前回の記事](https://dassimen.hatenablog.com/entry/2025/03/17/021607)）は、gemma3を動かして「ローカルでLLMが動いた！」という体験がメインだった。
当時のドキュメントには「7BモデルはRAM 8GB必要」「13BモデルはRAM 16GB必要」といった目安表があったはずだ。
今回ドキュメントを見ると、その表が消えていた。代わりに量子化まわりの説明が増えていた。

なぜ表が消えたのか。量子化とは何なのか。掘り下げていくとLLMの動作原理の話に繋がっていって面白かったので、そこから順番に書いていく。

## LLMはなぜメモリを大量に食うのか

GPT系のモデルはTransformerと呼ばれるアーキテクチャで作られている。入力されたテキストの断片（トークン）を、何十層もの変換層に通すことで次のトークンを予測する構造だ。

```
入力トークン
    ↓
[第1層の重み] → 変換
    ↓
[第2層の重み] → 変換
    ↓
  ...（32〜96層）
    ↓
次のトークン1個
```

この各層の変換をどう行うかを決めているのがパラメータ、つまり重み。
「7Bモデル」の7Bは70億個のパラメータ数を指す。
層の数と各層の幅を掛け合わせた総量がこの数字になる。層が深く広いほど複雑な概念を表現できるが、その分メモリも多く必要になる。

そして、1トークンを生成するたびに全層の全パラメータをメモリから読み込んで計算する必要がある。
70億個のパラメータをF16（16ビット浮動小数点）で保存すると、、、

```
70億 × 2バイト = 約14GB
```

になる。7Bモデルを動かすには最低14GBのメモリが必要で、しかも1トークンを出すたびにこの14GBを読み切る処理が走る。

## メモリバウンドという壁

「14GBを毎回読む処理も、GPUなら一瞬では？」と思った。RTX 4090を参考に考えてみる。

| 能力 | 値 |
|---|---|
| 演算性能（FP16） | 82.6 TFLOPS（82兆回/秒） |
| メモリ帯域 | 1,008 GB/s |

演算性能はすごい速い。だけどメモリ帯域には上限がある。
7Bモデル（14GB）で1トークン生成する理論上限を計算すると、

```
14GB ÷ 1,008GB/s ≈ 0.014秒 → 約70 tokens/s
```

GPUがいくら速くても、メモリからデータが来ないと演算ユニットは待つしかない。
演算性能ではなくメモリ転送速度がボトルネックになっているこの状態を「メモリバウンド」と呼ぶ。
LLMの推論はその典型例。

ChatGPTやClaudeのAPIサーバーが速いのは、GPUが高性能なだけではない。
大量のリクエストをまとめて処理するバッチ処理によって、重みの転送コストを1リクエストあたりでメモリの読み込みを少なくしてまとめて処理してる。
この辺りの仕組みは、それぞれのドキュメントがある。
興味がある方は、探してみてほしい。

```
バッチ処理あり：
  重み転送1回 → 100リクエスト分まとめて計算
  → 転送コストを100で割り算できる

バッチ処理なし（ローカル1人用途）：
  重み転送1回 → 1リクエスト分しか計算しない
  → 演算ユニットのほとんどが遊んでいる
```

Ollamaのようなローカル1人用途ではバッチ処理が効かないため、メモリバウンドからは基本的に逃げられない。

## 量子化がメモリバウンドを直接攻略する

量子化とは、パラメータを表現するビット数を削減する技術だ。

```
F16（16ビット）: 0.123456789... → 高精度で保存
Q8（8ビット）:   0.1234...      → 少し丸める
Q4（4ビット）:   0.12...        → さらに丸める
```

精度は落ちる。しかしその代わりにファイルサイズとメモリ使用量が激減する。

| 形式 | ビット数 | メモリ削減率 | 品質への影響 |
|------|----------|------------|------------|
| F16  | 16bit    | 基準        | なし |
| Q8_0 | 8bit    | 約50%削減   | ほぼなし |
| Q4_K_M | 4bit  | 約70%削減   | 実用上は軽微 |
| Q4_0 | 4bit    | 約75%削減   | やや劣化 |

Llama 2 13Bで具体的に見ると、F16では26GB（RAM 32GB以上が必要）がQ4_K_Mでは7.9GBになる。
70%のサイズ削減で、32GB必要だったマシンが12GBで動くようになる。

### 量子化するとむしろ速くなる

ここでやはり気になるのが量子化したことでそれをもとに戻す必要が必ず出てくるはずだということ。
Q4で保存された値をGPUで使うには計算前にdequantize（脱量子化）が必要で、このコストは確かに存在する。

LLMは基本メモリバウンドな処理。

```
F16の場合：
  転送: 14GB → 転送時間が遅い
  dequantize: なし

Q4の場合：
  転送: 3.5GB → 転送時間が1/4に
  dequantize: 転送待ちの間にGPUの別コアが並列処理 → ほぼタダ
```

GPUは数千のコアが並列動作している。
dequantizeは単純な整数演算なので、データ転送の待ち時間の中に隠蔽される。
「解凍コスト < 転送削減」が成立するため、量子化するとむしろ速くなる。

## 2024年末に追加されたKVキャッシュ量子化

モデルの重みだけでなく、推論中の計算キャッシュも量子化できるようになった。
2024年12月にOllamaに追加された機能。

Transformerは過去のトークンとの注意を計算して次のトークンを決める。
毎回ゼロから計算し直すのは無駄なので過去の計算結果をキャッシュしておく。これがKVキャッシュだ。

問題は、コンテキストが長くなるほどキャッシュも膨らむことだ。

```
8Bモデルのメモリ使用量（コンテキスト長別）：
  2K トークン:   KVキャッシュ 約0.3GB
  32K トークン:  KVキャッシュ 約5GB
  128K トークン: KVキャッシュ 約20GB
```

長い会話になると急に遅くなる現象は、これが原因のことが多い。KVキャッシュを量子化することでこの膨らみを抑えられる。

```bash
# Q8_0：KVキャッシュのメモリを約半減、品質劣化はほぼなし（推奨）
export OLLAMA_KV_CACHE_TYPE=q8_0
export OLLAMA_FLASH_ATTENTION=1  # 必須

# Q4_0：さらに1/3まで削減（品質への影響は要確認）
export OLLAMA_KV_CACHE_TYPE=q4_0

ollama run llama3.1:8b
```

`OLLAMA_FLASH_ATTENTION=1` が必要な点に注意。非対応のモデルやGPUでは自動的にF16にフォールバックされる。

## Q4_K_M の読み方

Ollamaのモデルタグで見かける `Q4_K_M` という表記を分解してみる。
- Q4が4ビット量子化
- KがK量子化方式という混合精度アルゴリズム
- MがMediumを指す。

K量子化は「重要な重みには高精度を、そうでない重みには低精度を割り当てる」アプローチで、単純なQ4_0より品質が高い。
品質・速度・メモリのバランスが最も取れている。

## 実際のコマンド

```bash
# Q4_K_Mで動かす（ほとんどのモデルのデフォルト）
ollama run llama3.1:8b

# モデルの量子化レベルを確認
ollama tags llama3.1

# KVキャッシュも量子化する（長いコンテキストに有効）
export OLLAMA_KV_CACHE_TYPE=q8_0
export OLLAMA_FLASH_ATTENTION=1
ollama run llama3.1:8b
```

## ハードウェア別の目安

量子化レベルとコンテキスト長が変わるので、同じモデルでも必要なメモリは大きく変わる。
ドキュメントから一律の目安表が消えた理由でもあると思う。

| 環境 | 快適に動く目安 |
|------|-------------|
| RAM 8GB | 3〜4B Q4（gemma3:4b、llama3.2:3bなど） |
| RAM 16GB | 13B Q4 / 7B Q8 |
| RAM 32GB | 30B Q4 / 13B Q8 |
| Mac M2/M3 16GB（統合メモリ）| 13B Q4_K_M が快適 |

VRAMに収まらずRAMにはみ出した場合、速度が5〜30倍低下することがある。
量子化でモデルをVRAM内に収めることが最も効果的。

## 量子化で変わったこと・変わらないこと

以前は「7BモデルはRAM 8GB必要」という目安がほぼ成立していた。
当時はF16で動かすのが当たり前だったので、一律の表が意味を持っていた。
今は量子化レベルとコンテキスト長が変数になったため、同じ表では表しきれなくなった。

変わらない本質は、LLMがメモリバウンドな処理だということ。
量子化はそのボトルネックを直接攻略する手法として機能する。
モデルの重みを量子化すれば転送量が削減されてむしろ速くなり、KVキャッシュを量子化すれば長いコンテキストでもメモリを節約できる。
VRAMに収めればRAM流出を防いで劇的な速度改善が得られる。

「久々に触ったら量子化という単語が出てきた」というところから始まったが、掘り下げるとLLMがなぜメモリを食うのかという話に繋がっていった。

やっぱりOllamaは、面白い。
ローカルLLMは、今後も楽しんでいこうと思う。
